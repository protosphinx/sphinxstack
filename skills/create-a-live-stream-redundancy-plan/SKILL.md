# create-a-live-stream-redundancy-plan

Redundancy works only when failure detection and switch authority are clear.

## When to use

- Use for events, broadcasts, webinars, worship, public meetings, commerce, and critical remote programs.
- Do not call two paths redundant when they share the same power, network, encoder, account, or operator.

## Procedure

1. Define program priorities, maximum interruption, acceptable degraded mode, audience, recording, captions, security, and platform commitments.
2. Map sources, switcher, audio, graphics, captions, encoder, network, DNS, platform, authentication, player, communications, and archive.
3. Identify common-mode dependencies and assign primary, backup, spare, or manual fallback.
4. Design independent power, network carrier, encoder, stream key or destination, audio path, caption path, and local recording where justified.
5. Define health signals, operator views, thresholds, switch steps, authority, audience message, and return criteria.
6. Prebuild slate, audio-only, low-bandwidth, backup URL, dial-in, and recorded replacement paths.
7. Protect accounts, keys, ingest endpoints, moderator roles, and backup access.
8. Rehearse source, audio, power, network, encoder, platform, caption, operator, and venue failures under load.
9. Record detection time, switch time, data or content loss, audience effect, and repair.

## Failure plan

- If failover risks two conflicting public streams, designate one publication authority and fence the other.
- If every live path fails, preserve local recording and publish the approved status and recovery plan.

## Done

- A redundancy plan records dependencies, shared risks, primary and backup paths, signals, authority, switches, degraded modes, and communications
- Failure rehearsals verify detection, failover, captions, security, local recording, audience routing, and safe return for each critical path
