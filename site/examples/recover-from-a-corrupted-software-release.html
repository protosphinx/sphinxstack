Worked case: restore trust when hashes disagree

Trigger: One software release version has different artifact hashes across regions, registry metadata was overwritten, build provenance is incomplete, edge caches contain mixed files, the prior release used the same runner, and a database migration already committed new records.

Can we roll back to the previous tag?
Not until its runner, registry, signing, cache, artifact, and runtime chain are independently trusted.
Should caches be purged immediately?
Preserve representative corrupted variants first unless active harm makes immediate containment necessary.
Can we rebuild from the same pipeline?
Use a clean isolated path from reviewed source and verified pinned dependencies.
What proves recovery?
Attested clean artifacts, independent runtime hashes, state-compatible behavior, reconciled data, revoked trust, and recurrence tests.

Failure rehearsal

The clean rebuild matches in two environments, but a canary host still serves a mixed cached asset. Traffic remains limited, cache keys and propagation are repaired, and independent runtime verification repeats before expansion.

Questions people actually ask

Does a signature prove a clean artifact?

Only if the signing identity, inputs, build, storage, and verification chain remain trusted.

Can the prior release be trusted?

Not when it shares the affected trust path without independent verification.

What happens to committed database changes?

Design rollback, forward repair, or restore to preserve valid committed effects.

When should evidence yield to containment?

When active harm requires immediate action; document what could not be preserved.

When is service fully restored?

After artifacts, runtimes, data, behavior, security, and business outcomes reconcile.
