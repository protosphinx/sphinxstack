Worked case: move a billing API without replaying charges

Trigger: A billing API must move hundreds of internal and partner consumers to a new provider, but response shapes, authentication scopes, idempotency, rate limits, webhook signatures, SDK defaults, and error behavior differ, while scheduled clients may be absent from recent telemetry.

Can we inventory consumers from the last 30 days of traffic?
No. Add credentials, contracts, code search, SDKs, jobs, webhooks, support, partners, and owner attestation.
How do we dual run charge creation?
Do not duplicate mutations. Shadow computation or reconcile provider-side outcomes safely.
Can the new auth scope be broader temporarily?
No. Access widening is a stop condition, not a migration shortcut.
What proves cutover?
Consumer-generated compatibility evidence, safe state transition, monitored health, and a rollback that preserves accepted mutations.

Telemetry absence does not retire a client.

Failure rehearsal

A dormant monthly client authenticates only during billing close. The old version remains supported, the owner receives a test window, and retirement pauses until the scheduled journey and rollback pass.

Questions people actually ask

Is schema compatibility enough?

No. Verify semantics, auth, errors, timing, limits, retries, and side effects.

Can mirrored mutations use test accounts?

Use controlled safe accounts only when provider effects and cleanup are understood.

How long should the old API remain?

Until contractual notice, consumer evidence, failover, and retirement gates pass.

Who proves consumer migration?

The consumer owner produces versioned journey and rollback evidence.

What if a consumer has no owner?

Maintain compatibility or escalate an explicit risk decision.
