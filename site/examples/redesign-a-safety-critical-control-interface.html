Worked case: make control authority and state visible

Trigger: A regional water utility redesigns a control-room interface after a mode-confusion event: stale sensor values looked current, two operators issued conflicting pump commands, alarms flooded, remote and local authority were unclear, color alone signaled contamination risk, and rollback could not blindly restore prior valve commands.

Can we make alarms brighter?
First make each alarm actionable, prioritized, attributable, and safe under flood conditions.
Should rollback restore old commands?
No. Physical state may have changed; use an approved safe-state transition.
What must every control show?
Current mode, freshness, authority, intent, pending state, acknowledgement, and consequence.
What proves redesign?
Representative operators pass normal, degraded, conflicting, stale, delayed, and emergency scenarios with independently validated safeguards.

Never display stale certainty.

Failure rehearsal

A remote command arrives after local authority takes control. The stale authority epoch is rejected and operators see why.

Questions people actually ask

Can color show severity?

Not alone.

Should all alarms sound?

Only according to actionable priority and context.

Can users test with mock data?

Use realistic simulation and hardware where consequence requires it.

What if freshness is unknown?

Show uncertainty and restrict unsafe control.

When can rollout expand?

After bounded live evidence and independent safety acceptance.
