Worked case: recover partial schema state

Trigger: A production migration adding a nonnull column and backfill times out behind a lock while old and new application versions keep writing, some shards committed DDL, replicas disagree, and the down migration would drop values already written by the new version.

Should we run the down migration everywhere?
No. First fence unsafe writers and map committed, partial, blocked, and unknown state per shard.
Can the migration table be marked complete?
Only after actual schema, data, replicas, and application assumptions reconcile.
The backup job is green.
Preserve current evidence and verify restore capability before relying on it.
What permits restart?
Rehearsed recovery, schema and data reconciliation, compatible applications, healthy replicas, and gradual writer restoration.

Protect invariants before migration status.

Failure rehearsal

A repair preview finds values created by the new application that the down migration would drop. The plan switches to forward repair, preserves those rows, and validates mixed-version compatibility before any writer resumes.

Questions people actually ask

Is DDL always transactional?

No. Verify actual database and operation semantics.

Should replicas serve reads during recovery?

Only after their schema, data, and lag reconcile with authority.

Can migration history be edited?

Not as a substitute for proving actual state.

When is restore preferable?

When verified recovery point, data loss, downtime, and committed effects support it.

How should repair queries run?

With bounded scope, preview, checkpoint, stop conditions, monitoring, and reconciliation.
