Worked case: govern a shared system under strain

Trigger: A shared system serves twelve product teams, but contribution decisions are informal, accessibility fixes can break consumers, exceptions never expire, maintainers are overloaded, and adoption metrics count package installs as success.

Can we mandate the next version and call every installed package adopted?
No. I need a consumer inventory, contribution governance, release evidence, bounded exceptions, and outcome-based adoption states.
Exceptions slow standardization, so can they remain undocumented?
That hides risk and system gaps. Each exception needs scope, owner, compensation, expiry, and a convergence or retirement decision.
What if the only maintainer is unavailable during a breaking fix?
The governance model must rehearse that failure, preserve release and rollback authority, and narrow the service promise to staffed capacity.

Installation is not verified adoption.

Failure rehearsal

An urgent accessibility fix changes focus behavior for several critical consumers while the primary maintainer is unavailable. The backup authority pauses broad release, tests representative consumers, publishes a bounded patch, and verifies rollback before resuming the normal contribution process.

Questions people actually ask

Who owns a design system?

Named maintainers operate it, while sponsors and consumer representatives hold explicit decision and risk roles.

Should adoption be mandatory?

Only when the system meets evidenced needs and the organization owns migration, support, and exception paths.

What makes an exception valid?

Specific scope, rationale, controls, owner, expiry, and a tested convergence or retirement plan.

How are breaking changes approved?

Through consumer impact, compatibility, accessibility, migration, and rollback evidence.

When should a component retire?

After supported consumers migrate or receive an accepted alternative and recovery evidence passes.
