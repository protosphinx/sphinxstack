Trigger: Our app deploys from a laptop and we need a repeatable path to production.

Only one engineer knows the production deploy command.

The app is reversible. Database migrations run automatically during startup.
That couples a reversible release to an unreviewed data change. We will separate and gate migrations before automating promotion.

Build once instead. The same verified artifact should move through staging and production with an integrity digest.

Evidence set

  • Pipeline run: source, tests, artifact digest, approval, environment, and result.
  • Rollback rehearsal: known-bad canary returns to the last good artifact in four minutes.
  • Release record: change summary, deployment evidence, health window, and outcome.

Failure rehearsal

The canary passes process health but checkout errors exceed the user-facing threshold. Promotion stops automatically, the previous digest is restored, and the checkout journey must pass before the pipeline reports recovery. The failed artifact remains retained for investigation.

Questions people actually ask

Why build only once?

Rebuilding can change dependencies or bytes. Promotion should move the exact artifact that passed review and tests.

How many pipeline stages are necessary?

Only stages that detect a defined risk or support a release decision. More stages without purpose add delay and false confidence.

Should production deploy automatically?

Automation and approval are separate choices. High-risk releases may require an authorized promotion after automated evidence is ready.

Where should secrets live?

In the deployment platform or secret manager with narrow environment access. They must not enter source, artifacts, or logs.

What is a successful rollback test?

The real mechanism restores a known-good release and the critical user journey passes within the recovery objective.
