Worked case: migrate a major shared UI release

Trigger: A major design-system release changes tokens, semantics, component APIs, focus behavior, and themes across unknown consumers that carry local overrides and cannot all migrate at once.

The codemod passes. Can we deprecate the old package next sprint?
Not until the consumer inventory, compatibility strategy, migration waves, behavior tests, exceptions, and rollback are reconciled.
Can teams visually spot any regressions?
Visual review misses semantics, focus, screen-reader behavior, local overrides, themes, and critical journeys. Each wave needs broader verification.
Some repositories have no owner.
Unknown or unowned consumers block retirement. We can isolate them, assign authority, or extend compatibility, but cannot silently abandon them.

A codemod proves transformation, not consumer safety.

Failure rehearsal

A focus fix passes the component story but traps keyboard users in a consumer's customized overlay. The wave stops, the affected product rolls back to the supported source, the compatibility strategy changes, and the consumer joins the next wave only after semantic, focus, and journey verification.

Questions people actually ask

Is installation a completed migration?

No. The rendered consumer must preserve behavior, semantics, accessibility, themes, and critical journeys.

How should waves be ordered?

By risk, representativeness, dependency, readiness, capacity, and reversibility.

When are compatibility layers useful?

When they create a bounded, testable bridge rather than indefinite hidden divergence.

What blocks retirement?

Unknown consumers, unresolved critical exceptions, failed verification, or unavailable rollback.

Should local overrides be removed?

Only after their purpose and impact are understood and the target system meets the need.
