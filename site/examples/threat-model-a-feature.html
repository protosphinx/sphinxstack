Worked case: add customer document uploads

Trigger: The feature crosses a trust boundary and handles data we would regret exposing.

Customers need to upload identity documents for account review.
We need the data classification, who may read it, retention, file limits, processing path, and release risk owner before implementation.
Review staff can read files. We planned to put them in the normal public asset bucket with hard-to-guess names.
That is not an authorization control. The bucket is a trust boundary and requires private storage with checked access.
Is file type validation enough?
No. We also need size limits, content inspection, isolated processing, safe download headers, retention, logging, and containment.

The review follows the data and authority.

Failure rehearsal

A storage policy accidentally permits public reads. The release monitor detects the configuration, the feature is disabled, access credentials are rotated, evidence is preserved, and the privacy owner decides notification. Recovery includes a cross-account test, not only a corrected policy screen.

Questions people actually ask

Is a threat model a security audit?

No. It is a design review that identifies important abuse paths and verifies mitigations. Some systems also need specialist testing or formal audit.

What is a trust boundary?

A place where identity, ownership, privilege, network, validation, or data classification changes.

Do we need to list every possible attack?

No. Cover credible paths to important assets, rank them with stated assumptions, and revisit the model as the design changes.

Who may accept a risk?

The named person accountable for the affected asset and consequence, under the organization's policy. A developer cannot silently accept it for others.

When should the model be updated?

When data flow, privileges, external dependencies, attacker opportunity, or the consequence of failure materially changes.
