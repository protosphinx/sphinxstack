Worked case: split a live name column

Trigger: We must change a live table without losing writes or taking the product offline.

We need to replace users.name with given_name and family_name this week.
Before commands: which readers and writers use the column, how large is the table, and has a current backup been restored successfully?
The API and two reports use it. Twelve million rows. Backups run nightly, but nobody has restored one lately.
Then restoration is the first gate. We will also expand the schema before changing either reader.
Can we rename the column and fix errors as they appear?
No. That creates an outage and makes rollback depend on hurried code. We will keep both paths compatible during the move.

The first migration step protects recovery.

The migration plan

  1. Add nullable new columns with no table rewrite.
  2. Deploy compatible code that writes old and new values.
  3. Backfill stable ID ranges in resumable batches.
  4. Reconcile null counts, samples, and application reads.
  5. Move reads, observe, then remove the old path in a later release.

Evidence set

  • Staging rehearsal: 12 million shaped rows, measured locks, duration, log growth, and lag.
  • Reconciliation query: old rows equal populated new rows plus reviewed exceptions.
  • Rollback proof: tested code revert, preserved old column, threshold, and named operator.

Failure rehearsal

Replication lag crosses the approved threshold during batch 14. The operator stops the resumable worker, records its checkpoint, and confirms lag returns to normal. Because old and new columns are still written, the application remains correct. The next run resumes at a lower batch rate after review.

Questions people actually ask

Why restore the backup before changing anything?

A backup is only a recovery option after a restore proves it can be read and meets the required recovery time.

What is expand and contract?

Add a compatible new shape, move traffic and verify it, then remove the old shape in a later release.

Can a migration be rolled back?

Sometimes. Code may be reverted while data cannot. The plan must state the last reversible point and when forward repair is safer.

Why batch the backfill?

Bounded batches limit locks and resource use, make progress measurable, and allow safe pause and resume.

When can the old column be removed?

After every reader and writer uses the new path, reconciliation passes, and the agreed observation and rollback window has ended.

Where to go from here

Use Design observability for integrity and lag signals, or Ship a data pipeline when historical records need controlled replay.
