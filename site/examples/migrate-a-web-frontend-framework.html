Worked case: migrate a commerce frontend without a rewrite outage

Trigger: A global commerce site must move from a client-only frontend to a server-rendered framework while preserving checkout, account state, saved carts, URLs, search indexing, analytics, accessibility, localized content, performance, and releases across hundreds of routes.

Can we rebuild every route and switch over in one release?
No. Inventory routes and outcomes, create a compatibility boundary, and migrate independently reversible vertical slices.
Matching screenshots should prove parity.
Screenshots miss state, focus, URLs, analytics, server rendering, performance, security, and assistive-technology behavior.
Can both runtimes update the saved cart?
Use one authoritative contract. Dual mutation creates divergence that rollback cannot safely resolve.
What blocks a migration wave?
Any unexplained behavior, accessibility, URL, analytics, security, or performance regression.

Failure rehearsal

A product-route canary resets keyboard focus and records purchase analytics twice. The wave pauses, traffic returns to the old route, and completed server orders remain untouched. Shared navigation and event ownership are repaired before the same parity suite runs again.

Questions people actually ask

Should migration start with shared components?

Start with representative vertical slices so shared boundaries are proven by real behavior.

Can old and new routers coexist?

Yes, through one explicit ownership and URL contract with independent rollback.

What counts as parity?

Equivalent user outcomes and approved quality attributes, not identical implementation.

When can old code be removed?

After traffic, references, support needs, observation, and rollback gates expire.

How should irreversible data be handled?

Keep server effects authoritative and make frontend rollback independent of data reversal.
