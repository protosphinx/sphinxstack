Worked case: recover users trapped between incompatible releases

Trigger: A frontend release publishes HTML that references missing hashed assets while a new service worker caches an incompatible application shell, an API schema changed, CDN regions hold different manifests, feature flags vary by session, and some customers report duplicate checkout attempts.

Should we redeploy the last frontend commit?
Only if APIs, data, schemas, flags, service workers, and in-flight user state remain backward compatible.
Can we tell customers to clear cache?
That is not a recovery plan. Publish a compatible path that reaches stale and clean clients.
Should a timed-out checkout retry?
Not until the authoritative server state resolves the original transaction outcome.
What is the unit of diagnosis?
The user's full version stack: HTML, assets, worker, cache, API, schema, flags, locale, session, and transaction.

A release is a distributed state across user and server layers.

Failure rehearsal

The prior frontend cannot read records written under the new API schema. The team blocks unsafe rollback, publishes a forward compatibility repair with immutable assets and a new worker epoch, routes new sessions safely, reconciles checkout intents, and verifies long-lived plus offline clients before restoring the action.

Questions people actually ask

Does a green deployment prove recovery?

No. Verify the actual user version populations and critical journeys.

Should every cache be purged?

Only through a scoped plan that preserves evidence and does not amplify origin failure.

Can a service worker activate immediately?

Only with proven compatibility, client coordination, and recoverable cache transitions.

What if no safe version exists?

Disable the affected action and communicate status while building a safe recovery path.

When is the incident closed?

After all version populations stabilize, user and financial state reconcile, and recurrence controls pass.
