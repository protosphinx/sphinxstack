Worked case: split only a proven boundary

Trigger: A commerce monolith shares one database across checkout, inventory, billing, support, reporting, sessions, caches, and jobs, while undocumented cross-module transactions, release bottlenecks, cascading incidents, and a six-month demand for four new services make a direct split unsafe.

Can teams each take their tables and build a service?
Not until domain, runtime, data, transaction, job, report, and failure dependencies are measured.
Should checkout be extracted first because it matters most?
Start with a coherent lower-risk boundary that proves ownership and operating controls.
Can both systems write during migration?
Only under one declared authority and reconciled transition; uncontrolled multi-writer state is a stop condition.
What proves the split works?
Behavior, data, permission, load, latency, cost, isolation, operations, and rollback parity at each wave.

Extract ownership, not folders.

Failure rehearsal

Shadow reads disagree because a report encodes an undocumented cross-module adjustment. The wave pauses, the dependency joins the inventory, ownership and contract are redesigned, and the report remains on the old path until parity is proven.

Questions people actually ask

Does every module need its own service?

No. Separate only boundaries that justify independent operation.

Who owns shared data?

Declare one authoritative writer and explicit read or workflow contracts.

Can a distributed transaction replace the old transaction?

Only after invariants, failure modes, compensation, and recovery are proven.

What is a good first extraction?

A coherent, measurable, lower-risk boundary with an accountable operator.

When can old code be deleted?

After consumers, data, recovery, and retention gates prove it obsolete.

Where to go from here
