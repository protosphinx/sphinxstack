Worked case: an orders API for two teams

Trigger: Two teams need to integrate without coordinating every code change.

The storefront needs to create orders in the warehouse service.
Give me the two consumer workflows, caller identity, retry behavior, and fields the warehouse can safely expose.
Create an order and read its status. The storefront retries when requests time out.
Then create must be idempotent. A timeout after commit cannot create a second order.
Can we just return database errors while we build it?
No. Consumers need stable error codes and retry rules. Internal messages can change and may expose private details.

Failure behavior is part of the interface.

The contract excerpt

POST /v1/orders
Idempotency-Key: 3ee1...

201 { "id": "ord_42", "status": "accepted" }
409 { "code": "ITEM_UNAVAILABLE", "retryable": false, "trace_id": "..." }
429 { "code": "RATE_LIMITED", "retryable": true, "retry_after_s": 5 }

Evidence set

  • Versioned schema: request, response, limits, null rules, and errors in source control.
  • Consumer examples: success, duplicate, validation, permission, rate limit, and timeout.
  • Compatibility check: CI rejects removal or narrowing of a published field.

Failure rehearsal

The provider makes a formerly optional field required. The schema comparison blocks promotion. If an incompatible version reaches staging, consumer contract tests fail before production. If it reaches production, the team rolls back the provider and notifies both named consumer owners.

Questions people actually ask

Is an OpenAPI file the whole contract?

No. The schema is central, but retry, authorization, compatibility, deprecation, ordering, and operational behavior also need explicit rules.

What does idempotent mean here?

Repeating the same intended operation has the same effect as doing it once, including when the first response was lost.

Should every change create a new version?

No. Prefer compatible additive changes. Create a new version when semantics must break and migration cannot preserve the old behavior.

What makes an error useful?

A stable code, safe human explanation, retry rule, relevant field where appropriate, and trace ID for support.

Who owns contract tests?

Provider and consumer owners share them. The provider proves compatibility while consumers prove the workflows they depend on.
