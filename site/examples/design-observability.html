Worked case: make checkout diagnosable

Trigger: The service is live, but we cannot tell whether users are succeeding or why requests fail.

We have CPU graphs and thousands of logs, but support finds checkout failures first.
Start with the user outcome. What exactly counts as a successful checkout, and within what time?
An accepted order ID within three seconds. Payment declines are expected, system errors are not.
Good. We can define the indicator without counting valid declines as service failure.
Should we alert when CPU reaches 80 percent?
Only if that condition requires a known action. The primary alert should be the failed user outcome.

User success determines the first signal.

Evidence set

  • Dashboard: user success, scope, provider health, queues, resources, and recent releases.
  • Alert test: a safe injected provider error pages once and links the correct runbook.
  • Diagnostic trail: one checkout ID connects the safe structured events and trace.

Failure rehearsal

The metrics pipeline is delayed during an incident. Operators compare a synthetic checkout and payment-provider acceptance counts before trusting the dashboard. A telemetry volume spike triggers sampling for low-value events while errors and state changes remain complete.

Questions people actually ask

What is a service level indicator?

A measured ratio or distribution that represents a user outcome, such as successful eligible checkouts or message delivery delay.

Do we need logs, metrics, and traces?

Use each only for a named question. Metrics show scope, logs record events, and traces connect work across boundaries.

What should trigger a page?

A symptom that needs timely human action and has a runbook. Informational conditions belong on a dashboard or report.

May we log request bodies?

Not by default. Log safe named fields and decisions. Personal data, credentials, and tokens require explicit need and handling rules.

How do we know the design works?

Inject a safe failure and prove the indicator changes, the alert routes once, and the runbook leads to verified recovery.
