Worked case: make telemetry loss an explicit system behavior

Trigger: A company wants one telemetry pipeline for logs, metrics, traces, security detections, and required audit events from three regions, but burst volume exceeds network capacity, customer data appears in attributes, downstream storage fails unpredictably, and nobody can quantify drops or restore the collectors.

Can every service just export everything to one central collector?
Not safely. Classify signals, failure domains, data rules, and permissible loss before choosing topology.
Should applications block when storage is down?
Only where an approved critical evidence contract requires it. Ordinary serving paths need bounded buffers and explicit shedding.
Could we drop the noisiest stream during a burst?
Yes, if priority is defined in advance, loss is counted, required evidence is protected, and coverage degradation is visible.
What proves recovery?
Restore configuration and critical flow, drain valid buffers, and reconcile produced, dropped, duplicated, and delivered records.

Design loss before overload chooses it.

Failure rehearsal

A regional storage outage fills disk buffers during a traffic burst. Debug logs shed first, security detections and audit events use their protected path, and every drop counter remains available. The team restores a gateway from controlled configuration, drains retained batches, marks duplicates, and publishes the bounded unrecoverable gap before consumers resume normal claims.

Questions people actually ask

Must telemetry be lossless?

No. Loss tolerance depends on signal purpose, but it must be explicit, prioritized, measured, and governed.

Can telemetry block a request?

Usually not indefinitely. Use a separately approved path for evidence whose durability justifies stronger coupling.

Where should redaction happen?

As close to the producer as practical, with defense-in-depth checks before shared storage.

How are tenants isolated?

Enforce authenticated routing, bounded attributes, storage separation, access controls, and tested queries.

What should a restore test include?

Configuration, credentials, routing, buffers, critical signals, counts, duplicates, gaps, and consumer acceptance.
