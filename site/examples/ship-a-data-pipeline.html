Worked case: make a daily orders feed reliable

Trigger: A daily data job must handle retries, late records, and backfills without corrupting reports.

Finance gets yesterday's orders from a nightly script, but reruns double the totals.
We need the source key, event and delivery time, correction rules, consumers, and a replay source before changing the job.
Order ID is stable. Refunds can arrive three days later. The raw export is kept for thirty days.
Then processing can be idempotent by order ID, and the published window needs controlled correction for late refunds.
Could the backfill write straight into the report table?
Not safely. It should write isolated output, reconcile against source, then promote atomically.

Replay behavior is designed before the next failure.

The pipeline contract

Identityorder_id plus source revision
Timeordered_at for business day; delivered_at for freshness
Correctionrefund updates may revise the prior three business days
Publishvalidated partition swaps atomically after reconciliation

Evidence set

  • Replay test: duplicate files, late refunds, malformed rows, and an interrupted run produce one correct result.
  • Reconciliation report: source, processed, quarantined, and published counts plus total value.
  • Operating runbook: pause, resume, replay, backfill, correction, and consumer notification.

Failure rehearsal

Publication fails after transformation. Because output is isolated, finance continues reading the last good partition. The operator preserves the checkpoint, repairs the publication permission, reruns the same bounded range, and promotes only after reconciliation passes.

Questions people actually ask

What makes a pipeline idempotent?

Stable identity, deterministic transformation, checkpoints, and atomic publication make retries produce the same intended result instead of duplicates.

Why keep raw input?

It provides a controlled replay source for recovery, corrections, audits, and new transformation versions, subject to privacy and retention rules.

How should bad records be handled?

Classify the rule: block the batch, quarantine the record, warn an owner, or measure the issue. Never silently discard it.

What is a backfill?

A controlled reprocessing of a historical range with versioned code, bounded load, isolated output, comparison, and explicit promotion.

How are consumers protected from corrections?

Name correction windows and notification rules, preserve lineage, and publish atomically so consumers never read a half-corrected dataset.
